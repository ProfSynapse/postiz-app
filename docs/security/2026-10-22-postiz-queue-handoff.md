# Postiz queue handoff for the Social Redis patch

Prepared locally for the n8n-data owner; no Railway, Redis or Postiz service was changed. This supplements the parent's `delegation/artifacts/n8n-data/README.md` and `rollout-plan.json` without modifying them. Their Social Redis plan is 8.2.1 → digest-pinned 8.2.9, retaining `/data`, existing authentication references and `save 60 1`; effective AOF, TLS and loaded persistence set remain unverified. Do not infer those settings from the command alone.

## Source inventory

`redis/redis.service.ts` constructs one ioredis client from `REDIS_URL`, with dual-stack DNS, `maxRetriesPerRequest:null` and a 10-second connection timeout. No BullMQ prefix or connection `db` override is passed. Thus the queue prefix is BullMQ's default **`bull`**, and DB selection comes from the URL (default **0** only when no index is supplied). The actual live URL/index, any provider prefix/wrapper and competing clients were not inspected. Confirm them privately on every backend/cron/worker replica; never print the URL.

`bull-mq-transport-new/strategy.ts` creates a Queue and Worker per registered handler. `apps/workers/src/app/{posts,plugs}.controller.ts` register **post, submit, sendDigestEmail, webhooks, cron, plugs, internal-plugs**. Each worker is configured with concurrency300 and maxStalledCount10, so do not equate the number of process instances with active-job concurrency. Backend services, MCP/AI tools, public/API routes and workers themselves can produce follow-up jobs. `apps/commands/src/tasks/check.stars.ts` also emits **check_stars, sync_all_stars, sync_trending**, and StarsService emits sync_all_stars; the inspected workers register no corresponding handlers. Inventory these orphan/legacy queues and other live consumers instead of deleting them.

`BullMqClient.dispatchEvent()` uses `data.id` or a fresh UUID as jobId, then spreads data.options (which can override jobId). Normal events remove both completed and failed jobs. Scheduler events use `upsertJobScheduler(data.id or UUID, {every, immediately}, template)` and remove completed/failed iterations. Nest10's `ClientProxy.emit()` connects its observable immediately; absence of an explicit subscribe is not proof an event was never emitted. The synchronous `publish()` request/reply override is a stub; do not base a recovery probe on `send()`.

- Post IDs normally equal the PostgreSQL parent Post ID. Creating/rescheduling posts, marketplace approval and cron reconciliation enqueue them. A duplicate ID deduplicates while the existing job remains; removal/completion permits that ID again.
- AutoPost activation/change calls `processCron()`, upserting scheduler ID = AutoPost ID, every3,600,000ms with immediately:true. Deactivation removes it. No boot routine rebuilding all active AutoPost schedulers was found. Recreating them can trigger an immediate run and change the next run time.
- `plugs`: IDs `plug_<postId>_<identifier>`; `internal-plugs`: `plug_<postId>_<trigger>_<integrationId>`. They can enqueue follow-ups while executing. A removed job ID is reusable.
- Digests and webhooks use distinct queues but both use job ID `digest_<orgId>` and delay60,000ms. Their `digest_<orgId>` / `webhook_<orgId>` Redis keys have 60-second TTLs. Those keys throttle requests; they are not durable delivery ledgers.
- Post publishing has a separate `post:publishing:<id>` NX/PX lock with a 20-minute TTL and token-checked Lua release. It is not a renewable, permanent deduplication record. Non-recurring already-PUBLISHED posts are skipped, but an external success followed by death before DB commit can replay; recurring posts intentionally bypass that skip. Never promise exactly-once effects.
- The strategy catches handler errors and calls `job.discard()` without rethrowing; controllers also catch errors. A completed/removed BullMQ job is not proof the provider action succeeded. Reconciliation must include PostgreSQL state and external outcome evidence. No real provider was called in this preparation.

## Reconstruction limits

`PostNowPendingQueues` runs every minute and considers only parent, undeleted QUEUE posts, eligible integrations and publishDate between two minutes and two hours ago. It respects an active publish lock; missing jobs or overdue waiting/delayed jobs can be removed and immediately requeued. `CheckMissingQueues` runs at minute0 each hour and looks only at eligible parent QUEUE posts between now and three hours ahead; it recognizes waiting/delayed states, not active. Neither covers a whole empty Redis, posts more than three hours away, more than two hours overdue, all ancillary jobs or all repeat schedules. Keep both cron jobs stopped during inventory and reconciliation. Do not wait for them to repair a lost queue.

Cron also runs token refresh, the gated media janitor and `WorkerSupervisor`. The supervisor checks every minute after a three-minute boot grace and may `pm2 restart workers` after a five-minute cooldown. Stop **cron** before intentionally stopping workers. Heartbeats are `postiz:heartbeat:workers:<hostname>`, interval15s, TTL60s, and only beat after all workers report ready/running; use the current host's key, not an old deployment's.

## Exact owner-run cutover checks

These are future authorized maintenance actions, not commands executed against production here.

1. Recheck the parent's scoped Social Redis service/deployment/image/mount IDs and target digest immediately before the window. Inventory every Postiz replica, command runner and any other client of that Redis DB. Preserve the same database index, prefix, auth/TLS references, mount and save policy. Record `INFO server`, safe fields from `INFO persistence`, and only `CONFIG GET dir dbfilename appendonly appenddirname appendfsync save maxmemory-policy tls-port`. Use private console/secret references; never query requirepass/masterauth/whole ACL configs or print URLs. Confirm noeviction suitability; do not change policy incidentally.
2. Close Postiz ingress and API/webhook/MCP producers through the owner's maintenance route, and stop **frontend, backend, cron** in every application container. Those are the repository's actual PM2 names. Stop command runners too. Workers can emit follow-ups, so globally pause **all inventoried BullMQ queues** and record each queue's original pause state. Pausing does not stop active work. Allow active jobs to finish while producers remain closed; require active=0 for every queue on repeated observations and no unexplained new jobs. Do not try to drain future delayed jobs or an hourly scheduler to zero.
3. Before stopping workers, correlate any in-flight provider action with its Post row/provider receipt and outstanding publish lock. The production shutdown implementation returns before all worker.close promises settle, and normal PM2 timeouts alone do not prove drain. Stop workers only after active=0; provide enough teardown time for connections. Do not force-remove locks or active jobs. If a worker died mid-effect, quarantine that Post for owner reconciliation before replay.
4. With all clients stopped, take the owner's tested Redis persistence checkpoint and matched Postgres checkpoint as required by n8n-data's plan. Record loaded RDB/AOF mode and checkpoint ID/checksum in protected backup storage. Record count plus ID/time/scheduler inventories without job payloads: Redis LLEN/LRANGE for wait/paused/active, ZCARD/ZRANGE WITHSCORES for delayed/prioritized/repeat, and only metadata HMGET(timestamp, delay, name, attemptsMade, processedOn, finishedOn) on job hashes. Use SCAN with bounded pages to discover other `bull:*:meta` queues, not KEYS. Hash IDs for shared receipts; compare Post IDs using the same hash. Do not HGETALL job hashes, read the data field, or publish job templates. Bound list pages and explicitly fail/continue on a cap instead of silently omitting entries.
5. Rehearse the target binary with a copy of that checkpoint on fresh isolated storage and blocked egress under owner authority. This preparation uses dummy fixtures only, not a copied live queue. Upgrade Social Redis to the exact 8.2.9 digest, retain `/data` and the verified command/settings, and verify actual process version, authentication, persistence, index, prefixes and inventories before reconnecting any client. Paused queues should remain paused. Restore from a cold pre-cutover checkpoint if format compatibility fails; never overwrite the old volume to experiment.
6. Start the **workers** in a maintenance launch with queues still globally paused, then backend for diagnostics with ingress still closed. Keep cron stopped. The normal image CMD runs `pm2 delete all`, `prisma db push`, and starts all four processes together: it is unsuitable for enforcing this order unchanged. The owner must review a temporary maintenance command/process split first (for example explicit `pm2 start pnpm --name workers --cwd /app/apps/workers -- start`, then the analogous backend command), preserve required environment references, and avoid an unreviewed production schema push. No such production override was made here.
7. Compare all pre/post inventories and due times exactly, allowing only explained clock progression and the fixture canary. Verify DB QUEUE parents both inside and outside cron windows, PUBLISHED/ERROR rows, recurring posts, active AutoPosts and every stored repeat scheduler/next timestamp. For orphan/ancillary queues consult the owner; do not reconstruct digests/webhooks/plugs by indiscriminate re-emission. Recover a missing scheduler only from approved DB/config evidence and an agreed next run time; `immediately:true` is not neutral. Review interrupted provider outcomes before replaying posts; the Redis lock/DB guard does not resolve the external-success crash window.
8. Require current-host heartbeat readiness and `/health/deep` success, expected waiting/delayed counts, zero unexplained failed/stalled/active changes, and a nonpublishing canary. Resume only queues that were running originally, then restore cron and ingress under owner approval. Observe at least one due-delay and hourly-repeat boundary plus token refresh; explain missed timers. Never treat a heartbeat or empty queue alone as acceptance. On rollback keep all producers/consumers stopped and restore matched checkpoints only after accounting for external effects since cutover; blind snapshot replay can duplicate posts.

## Reproducible dummy evidence

`scripts/security/isolated-infra.ts` refuses non-fixture DB/Redis hostnames before importing their clients. Its seed phase uses actual Prisma schema/relations/transaction rollback/bcrypt, actual BullMqClient, and actual publish-lock Lua/NX behavior. It writes waiting, one-hour delayed and hourly scheduler jobs into a disposable Redis. After a real RDB save and container restart, consume compares IDs, timestamps, delays and scheduler metadata, then uses the actual BullMqServer with only two workers and harmless Prisma media inserts. It probes the real HealthController, heartbeat and repeat preservation, and demonstrates that reusing a completed job ID can run it again. Final execution results and any limits are in the round2 receipt; this paragraph describes the fixture, not live rollout evidence.
